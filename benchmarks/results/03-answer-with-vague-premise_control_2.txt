这是一个非常经典的性能问题。数据库慢导致接口 500（通常是超时或连接池耗尽），**核心思路是：先定位瓶颈，再分层次优化**。千万别上来就改代码。

我帮你梳理一套从“排查”到“解决”的标准化流程，按优先级排序：

### 第一步：快速止血（5分钟）
先恢复服务，再谈优化。

1.  **杀掉慢查询**：在 MySQL 中执行 `SHOW PROCESSLIST;` 找到 `Time` 很长的 `SELECT`，用 `KILL id;` 直接杀掉。
2.  **重启连接池**：如果连接池被占满，重启应用服务通常会释放连接（临时有效）。
3.  **降级/限流**：如果流量异常，先通过网关限流，防止数据库被拖垮。

---

### 第二步：定位到底是谁“慢”（15分钟）
**不要猜，用数据说话。**

1.  **开启慢日志**：
    ```sql
    SET GLOBAL slow_query_log = ON;
    SET GLOBAL long_query_time = 1;  -- 记录超过1秒的SQL
    SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';
    ```
2.  **查看数据库监控**（如果是云数据库，看控制台）：
    - 是 **CPU 飙升**（复杂计算/扫描）？
    - 还是 **IOPS 打满**（磁盘读写瓶颈）？
    - 还是 **锁等待**（`SHOW ENGINE INNODB STATUS\G` 看死锁）？
3.  **查看慢日志**：找到最频繁出现的 SQL 语句。

---

### 第三步：对症下药（核心优化策略）

根据第二步的定位，通常分以下几种情况处理：

#### 情况A：SQL 本身没走索引（最常见）
**症状**：`EXPLAIN` 看到 `type=ALL`（全表扫描）或 `rows` 扫描行数巨大。

**优化手段**：
- **加联合索引**：针对 `WHERE` 和 `ORDER BY` 的字段建索引。
- **覆盖索引**：`SELECT` 的字段尽量是索引的一部分，避免回表。
- **避免隐式转换**：比如字段是 `varchar`，你传入 `int`，会导致索引失效。

#### 情况B：SQL 逻辑太重（搞垮 CPU）
**症状**：`CPU` 飙到 100%，慢日志里是复杂的 `JOIN` 或 `LIKE '%xxx%'`。

**优化手段**：
- **减少 JOIN**：应用层拆分成多次查询，用内存组装（空间换时间）。
- **避免 `SELECT *`**：只取需要的字段，减少 IO 和内存占用。
- **分页优化**：`LIMIT 100000, 20` 是很慢的，改成 `WHERE id > 上一次的id LIMIT 20`（延迟关联）。

#### 情况C：数据量太大了（单表过大）
**症状**：索引建了也慢，单表数据超过 2000 万行。

**优化手段**：
- **归档历史数据**：把 3 个月前的数据移到归档表或冷存储。
- **分库分表**（ShardingSphere/MyCat）：按用户 ID 或时间取模。*这是最复杂的方案，慎用。*
- **冷热分离**：热数据放 Redis，冷数据放 MySQL。

#### 情况D：数据库配置有问题（硬件背锅）
**症状**：IO 很高，但数据量不大。

**优化手段**：
- **调整 Buffer Pool**：`innodb_buffer_pool_size` 设置为物理内存的 60%-70%。
- **开启读写分离**：主库写，从库读（用 ProxySQL 或云数据库只读实例）。

---

### 第四步：架构层面优化（长期方案）
如果 SQL 和索引已经优化到了极限，还是慢，说明**单库已经扛不住了**，需要上缓存和队列：

1.  **加 Redis 缓存**（性价比最高）：
    - 查询流程：先去 Redis 查，没有再去 MySQL，然后写回 Redis。
    - **预防缓存穿透**：查不到也缓存空值（TTL 短一些）。
    - **预防缓存击穿**：用 `setnx` 加互斥锁，只允许一个请求去查数据库。
2.  **异步化**：
    - 如果接口返回的数据**不需要实时**（比如报表/统计），直接返回“处理中”，后台用消息队列（RabbitMQ/Kafka）异步查询数据库。
3.  **引入 ES（Elasticsearch）**：
    - 如果是复杂的搜索（`LIKE`），直接走 ES，MySQL 只做主存储。

---

### 第五步：代码层排查（很隐蔽的慢）
有时候 SQL 很快，但接口还是慢，可能是因为：

- **N+1 查询**：循环查数据库 100 次。
- **长事务**：开启事务后，在事务里查询了远程接口（网络消耗导致锁长时间不释放）。
- **死锁重试**：频繁报 `Deadlock found`，Spring 自动重试导致耗时翻倍。

---

### 总结：别只调数据库，要做“前置拦截”

一个标准的优化流程图如下：

```text
用户请求
   ↓
[1] 静态数据? -----> 是 -----> 放CDN (基本不碰服务器)
   ↓否
[2] 热点数据? -----> 是 -----> 放Redis (缓存, 命中率99%)
   ↓否
[3] 复杂搜索? -----> 是 -----> 走ES (搜索引擎)
   ↓否
[4] 以上都不是 -----> 访问 MySQL (走索引, 加连接池)
```
