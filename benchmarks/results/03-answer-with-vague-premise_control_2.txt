面对数据库慢导致的 500 错误，这是典型的**后端性能瓶颈**问题。优化需要从**表象排查**到**根因治理**，再到**架构兜底**，分三步走。

以下是系统性的优化方案，按紧急程度排序：

### 第一步：立即止血（先恢复业务）
在优化数据库之前，**必须**保护你的应用服务器不被拖垮。

1.  **熔断与降级（最紧急）**
    -   **现象**：数据库连接池被占满，新的请求全部排队等待，最终超时返回 500。
    -   **方案**：在 Service 层或网关层引入 `Resilience4j` / `Sentinel` / `Hystrix`，对查询数据库的方法设置**超时时间**（如 2秒）。超时直接抛出降级异常，返回备用数据或错误提示，**绝不能让一个慢查询阻塞线程池**。
2.  **限流（保护下游）**
    -   如果慢是因为流量瞬间激增（如热点事件），需要在网关层对特定接口做限流（如 `QPS=1000`），超出的请求直接快速失败，避免压垮数据库。

---

### 第二步：定位与根因分析（找出为什么慢）
500 是结果，**慢是原因**。查看慢查询日志和监控大盘，归类原因：

| 典型症状 | 排查点 | 验证方法 |
| :--- | :--- | :--- |
| **单条查询慢** | SQL 没走索引、索引失效 | 打开 `slow_query_log`，用 `EXPLAIN` 分析执行计划 |
| **CPU 飙高** | 大量聚合计算、排序在内存/磁盘 | 查看 `SHOW PROCESSLIST;` 看是否有长时间 `Copying to tmp table` |
| **I/O 瓶颈** | 数据量过大，内存命中率低 | 查看 `Innodb_buffer_pool_read_requests` 与 `reads` 的比例 |
| **锁竞争** | 行锁/表锁冲突，阻塞等待 | 查看 `show status like 'Table_locks%'` 和 `innodb_row_lock%` |

---

### 第三步：针对性深度优化（核心方案）

#### 方向 A：索引优化（性价比最高）
-   **联合索引**：如果查询有 `WHERE` 和 `ORDER BY`/`GROUP BY`，建立联合索引。例如：`WHERE status=? ORDER BY create_time` 应建 `(status, create_time)` 索引。
-   **覆盖索引**：让查询的列完全包含在索引中，避免“回表”。例如查询 `SELECT name FROM users WHERE age>20;` 建 `(age, name)` 索引。
-   **避免索引失效**：禁止在索引列上使用函数（`WHERE DATE(time)=...` 应改为范围查询 `WHERE time >= ... AND time < ...`），禁止隐式类型转换。

#### 方向 B：SQL 重写（消除非必要开销）
-   **深分页问题**：`LIMIT 100000, 20` 会导致数据库扫描 100020 行。**优化**：改为 `WHERE id > 上一页最后一条ID LIMIT 20`（基于游标的分页）。
-   **`SELECT *` 改为 `SELECT 具体字段`**：减少网络传输和内存占用。
-   **拆分长事务**：一个大事务锁表 5 秒，不如拆成 10 个小事务，每次 0.5 秒，减少锁持有时间。

#### 方向 C：数据库配置调优（硬件利用率）
-   **MySQL InnoDB**：
    -   `innodb_buffer_pool_size`：建议设置为物理内存的 **60%-75%**。如果命中率低于 95%，说明这个值太小。
    -   `innodb_flush_log_at_trx_commit`：如果对数据丢失容忍度较高（支付类除外），从 1 改为 2，可减少磁盘 I/O，大幅提升写入速度。
-   **PostgreSQL**：
    -   `shared_buffers`：设为内存的 **25%**。
    -   `work_mem`：适当调大（如 16MB），减少磁盘排序（临时文件）的概率。

---

### 第四步：架构级优化（立竿见影的降本增效）

#### 方案一：引入缓存（读密集场景）
-   **本地缓存**：`Caffeine`（Java）/ `LRU`，适合极热数据（如配置、用户基本信息），延迟 <1ms。
-   **分布式缓存**：`Redis`。
    -   **旁路缓存策略**：先查缓存，未命中查库，然后写回缓存。
    -   **防击穿**：使用互斥锁（`SETNX`）保证热点 key 过期时只有一个线程去查库。
    -   **防雪崩**：缓存 TTL 设置随机时间（如 5 分钟 + 随机 0-300 秒），防止同时大面积失效。

#### 方案二：分库分表（数据量巨大时）
-   **表数据量 > 1000万行** 且索引优化无效时，考虑分库分表。
-   **原则**：按业务维度分片（如 用户ID 取模），避免跨库 JOIN（在应用层拼接）。

#### 方案三：读写分离（写少读多场景）
-   主库只负责写入和修改，从库负责查询。
-   **注意**：需要配置主从延迟监控。如果对实时性要求高（如刚下单查询订单），可以强制走主库（强一致读）。

---

### 第五步：利用工具缓解峰值压力
-   **异步化**：非必要的实时计算（如生成报表、发送通知），投递到 MQ（RocketMQ/Kafka），让接口秒回，数据库慢慢消费。
-   **静态化**：访问频率极高的页面（如首页、详情页），直接生成 HTML 放 CDN，连数据库都不访问。

---

### 优先级总结（行动清单）
1.  **今天就要做的**：给数据库连接池加超时机制（如 `durid` 的 `maxWait=2000`），接口加熔断。**防止 500 扩大化**。
2.  **本周要做的**：抓取慢 SQL，使用 `EXPLAIN` 添加联合索引；调整 MySQL `innodb_buffer_pool_size` 配置。
3.  **本月要做的**：根据业务场景，对热点数据增加 Redis 缓存层；重写深分页逻辑。

**特别提醒**：优化完成后，**请务必做压测**（如 使用 `JMeter` 模拟 1000 并发），观察 TP99 延迟是否降至 500ms 以内，以验证优化效果，而不是靠感觉“应该快了”。
