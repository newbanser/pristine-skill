数据库慢导致接口 500，这需要从 **“缓存”**、**“索引”**、**“SQL”** 和 **“架构”** 四个维度逐一排查和优化。

通常我们的处理策略是：**先止血（让接口不报错）→ 再治本（提升数据库性能）**。

以下是具体的排查和优化路线图，按优先级排序：

### 第一步：紧急止血（避免雪崩）
在数据库还没优化好之前，必须先防止所有请求都打到数据库上。

1.  **接口级缓存（Redis / Memcached）**：
    -   对于读多写少的数据，在 Service 层加缓存。
    -   **设置过期时间**（TTL），防止缓存击穿。如果数据一致性要求不算特别高（比如 5 秒内可容忍），这是性价比最高的方案。
2.  **限流与熔断（Sentinel / Hystrix）**：
    -   当数据库响应超时（比如超过 500ms），直接熔断该接口，返回一个兜底数据（如 “系统繁忙”），而不是让上层不断重试把数据库压垮。
    -   防止因一个接口慢，拖垮整个 Tomcat 线程池，导致其他接口也 500。

---

### 第二步：排查慢 SQL（治本关键）
90% 的数据库慢都是 SQL 或索引问题。先去数据库执行：

```sql
-- 查看最近执行时间较长的慢查询日志（MySQL）
SHOW VARIABLES LIKE 'slow_query_log';
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1; -- 超过1秒记录

-- 或者实时查看正在执行的SQL，看是否锁表
SHOW PROCESSLIST;
```
**优化方向：**

-   **建立联合索引**：针对 `WHERE`、`ORDER BY`、`GROUP BY` 涉及的字段建立组合索引，遵循**最左前缀原则**。
-   **避免索引失效**：不要在索引列上使用函数、隐式类型转换、`LIKE '%xxx'`。
-   **拆分大 SQL**：如果 SQL 关联了 5 张表以上，考虑拆分成多条小 SQL 在 Java 代码中合并（或者用子查询替代）。

---

### 第三步：优化数据库连接池与配置（提升吞吐量）
如果数据库 CPU 不高，但是响应慢，通常是连接池不够用或配置不合理。

1.  **调整连接池大小（HikariCP / Druid）**：
    -   默认的 `maximum-pool-size` 可能太小（如 10），在并发高时会导致线程等待。
    -   经验公式：`核心数 * 2 + 高效磁盘数`。可以适当调大，但**不要超过数据库 `max_connections` 的 70%**。
2.  **检查并发写冲突**：
    -   如果 SQL 是 `UPDATE ... WHERE`，检查是否产生锁等待。尽量用主键作为条件更新，避免扫表锁。

---

### 第四步：应用层优化（减少数据库负担）
-   **批量操作**：N+1 查询问题。原来是 `for` 循环查库，必须改成 `IN (...)` 批量查询。
-   **分页优化**：深分页 `LIMIT 100000, 20` 非常慢。改用 **游标分页**（`WHERE id > ? ORDER BY id LIMIT 20`）。
-   **异步化**：如果接口里包含非核心逻辑（如写日志、发通知），用线程池或 MQ 搞成异步，快速返回给前端。

---

### 第五步：硬件与架构层面（终极方案）
如果以上都做了还慢，那就是数据量太大或硬件瓶颈。

1.  **索引与底层存储优化**：
    -   对大数据量（如千万级）的表，考虑分库分表（ShardingSphere / MyCat）。
2.  **读写分离**：
    -   将报表、统计等重查询打到从库，主库只处理核心读写。
3.  **硬件升级**：
    -   检查磁盘是否是 HDD（机械硬盘），**换成 SSD/NVMe** 通常对随机读提升非常明显。
    -   增加内存，让 InnoDB Buffer Pool 能装下更多热数据，减少磁盘 IO。

---

### 第六步：监控与告警（防止复发）
-   在慢 SQL 日志中加入 `EXPLAIN ANALYZE` 查看执行计划。
-   使用 **DBA 神器**（如 SkyWalking、Prometheus + Grafana）监控数据库连接数、QPS（每秒查询数）、TPS（每秒事务数）和慢查询数。
-   如果数据库负载过高，看是 **CPU 高**（计算多，如正则模糊匹配）还是 **IO 高**（全表扫描），对症下药。

---

### 总结排查顺序
1.  **先看 `SHOW PROCESSLIST`**：看是不是大量的 `Waiting for table lock`（锁表）或 `Sorting result`（排序）。
2.  **用 `EXPLAIN` 看执行计划**：看 `rows` 扫描行数是不是百万级。
3.  **加缓存 + 加索引**（解决 80% 的问题）。
4.  **如果数据量真的特别大**，直接上 **分库分表**，单纯调优救不了。

**补充提醒**：如果用的是 MyBatis，检查一下有没有 `<collection>` 导致的嵌套查询，改成 `JOIN` 或分级查询。如果是 JPA，注意别让 Entity 在循环中触发懒加载。
