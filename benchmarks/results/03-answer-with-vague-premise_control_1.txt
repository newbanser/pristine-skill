这是一个非常常见的运维问题。数据库慢导致接口 500，通常不是单一原因，而是一个**链路问题**。直接“优化数据库”可能不够，建议按照**监控定位 -> 分层优化 -> 容量评估**的顺序来推进。

以下是系统性的排查与优化指南：

### 第一步：先“止血”与定位（确认 500 的根源）
在动数据库之前，先确认 **500 到底是数据库抛的，还是应用层超时导致的**。

1.  **看应用日志**：
    -   搜索 `TimeoutException`、`Connection pool exhausted`（连接池耗尽）、`Deadlock`（死锁）。
    -   如果日志显示等待获取连接超过 30 秒，那可能是**连接池不够**，而非 SQL 本身慢。
2.  **看数据库监控**：
    -   确认数据库 CPU 是否 100%？还是 IOPS 打满？还是慢查询日志突然暴增？
    -   **关键指标**：`Threads_running`（运行线程数）是否飙升？`QPS`（每秒查询数）是否正常？

---

### 第二步：分“三层”优化（核心方法论）

#### 1. 应用层优化（最便宜，见效最快）
很多“数据库慢”其实是**应用没写好**。

-   **检查 N+1 查询**：是否在循环中查了数据库？例如查询用户列表时，在循环里查每个用户的订单。
    -   *优化*：改为一次性 `JOIN` 或 `IN` 查询。
-   **检查连接池配置**：
    -   如果 `maxPoolSize` 设置太小（如 5），而并发请求 50 个，必然会有 45 个线程阻塞等待，最终报 500。
    -   *优化*：调大连接池（如 50-100），但需同步评估数据库最大连接数。
-   **添加缓存（Redis）**：
    -   针对**读多写少**且实时性要求不高的接口（如首页数据），在应用层加 Redis 缓存。缓存穿透时，使用互斥锁（`SETNX`）防止所有请求同时打穿到 DB。

#### 2. SQL 与索引优化（最常见痛点）
用 `EXPLAIN` 分析慢 SQL，重点看 `type` 和 `rows`。

-   **索引优化**：
    -   **未命中索引**：`WHERE` 条件列是否加了索引？`LIKE '%xxx'` 会导致索引失效。
    -   **索引选择性太差**：如果索引列只有 0 和 1 两个值，数据库会放弃索引全表扫描。
    -   **联合索引最左前缀原则**：`(a, b, c)` 索引，查询只用 `b` 字段是走不了索引的。
-   **回表优化（覆盖索引）**：
    -   如果查询 `SELECT *` 只为了拿一个字段，可以考虑将字段加入联合索引，避免回表查询。
-   **深分页问题**：
    -   `LIMIT 1000000, 20` 是慢查询重灾区。数据库需要先读取前 100 万行再丢弃。
    -   *优化*：改用 `WHERE id > 上一页最大ID LIMIT 20` 或延迟关联（先查子查询 ID 再 JOIN 原表）。

#### 3. 数据库架构与配置优化（硬件与架构）
如果以上都做了还慢，就是数据库本身扛不住“读写并发”了。

-   **读写分离**：
    -   主库负责写，从库负责读。绝大多数系统读占 80% 以上，这能极大分摊主库压力。
    -   *注意*：需容忍主从延迟（如 1 秒内）。
-   **分库分表（Sharding）**：
    -   单表数据量超过 2000 万（或 5000 万）时，即使有索引，B+Tree 树深度增加，随机 IO 变多，性能急剧下降。
    -   *策略*：按用户 ID 哈希或按时间分表。
-   **配置调优（缓冲池）**：
    -   **InnoDB Buffer Pool**：是否足够大？如果命中率低于 95%，说明内存不足，应调大该参数（通常设为物理内存的 60-70%）。
    -   **慢查询日志**：确认 `long_query_time` 设置为 1 秒，并开启 `log_queries_not_using_indexes`。

---

### 第三步：针对“接口 500”的专项优化（流量治理）

如果数据库本身没问题，是**瞬间流量暴增**导致的，需要做**限流和降级**。

1.  **熔断降级**：
    -   在接口调用数据库前，引入 Sentinel 或 Hystrix。如果数据库响应时间超过阈值（如 2 秒），直接返回兜底数据（如空白页或提示“稍后重试”），**不要**让请求堆积在数据库上，避免数据库被拖垮（缓存雪崩）。
2.  **队列削峰**：
    -   如果是**写操作**（如秒杀），把请求写入 MQ 队列，后端异步慢慢消费，减少数据库瞬间压力。

---

### 第四步：应急处理（数据库已经 500 了怎么办？）

如果现在数据库已经 CPU 100% 或连接数打满：

1.  **立刻杀掉长事务**：
    ```sql
    -- 查找超过 10 秒的事务
    SELECT * FROM information_schema.innodb_trx WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 10;
    -- 然后 kill 对应的 trx_mysql_thread_id
    ```
2.  **临时限流**：
    -   在网关层（Nginx）对特定接口配置 `limit_req`，拒绝多余请求，保住数据库最后一口“气”，恢复服务，再查根因。
3.  **分析慢日志**：
    -   找出 `rows_examined`（扫描行数）最多的语句，这通常是元凶。扫描 1000 万行只返回 1 行，这是性能杀手。

---

### 总结：最实用的建议清单

| 优先级 | 动作 | 预期效果 |
| :--- | :--- | :--- |
| **P0（立即）** | 查看 `EXPLAIN` 慢查询 | 通常能解决 70% 的问题（补索引）。 |
| **P0（立即）** | 检查应用连接池大小是否匹配并发量 | 解决连接等待超时导致的 500。 |
| **P1（今日）** | 对高频热点数据加 Redis 缓存 | 降低数据库 QPS 压力 50% 以上。 |
| **P1（今日）** | 开启数据库慢查询日志，持续监控 | 建立基线，防止复发。 |
| **P2（本周）** | 评估是否引入读写分离（主从架构） | 解决读并发瓶颈。 |

**最后提醒**：数据库大多数“慢”，**90% 的情况不是数据库“硬件”慢，而是 SQL 写烂了（没走索引）或索引失效了**。先 `EXPLAIN` 看一下执行计划，通常立竿见影。
