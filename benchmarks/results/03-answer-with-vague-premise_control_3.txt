面对接口返回 500 且怀疑是数据库慢导致的，我们需要系统性地排查和优化。直接盲目加索引或改代码往往收效甚微，**应该遵循“定位 → 分析 → 优化”的流程**。

以下是分阶段的优化策略，从**应急**到**根治**：

### 第一阶段：应急处理（止血）
在找到根因前，先防止系统雪崩。

1.  **加缓存（兜底）**：
    *   如果数据允许短暂的不一致（如 5-10 秒），**优先上 Redis 缓存**。这是解决“读多写少”场景慢查询的最快方式。
    *   如果 SQL 计算复杂（如聚合报表），缓存结果集。
2.  **降级与限流**：
    *   如果数据库 CPU/IO 已经 100%，网关层临时开启限流，保护数据库不被拖垮。
3.  **快速扩容**：
    *   如果是云数据库，先临时升级规格（CPU/IOPS），争取排查时间。

---

### 第二阶段：定位瓶颈（找到“慢”在哪）
不能凭感觉猜，要用数据说话。

1.  **查看慢查询日志**：
    *   **开启并定位**：`SHOW VARIABLES LIKE 'slow_query_log%';` 确认开启，查看 `mysqldumpslow` 或 `pt-query-digest` 生成的日志，找到 **Top N 的慢 SQL**。
    *   **关注指标**：Rows_examined（扫描行数）、Rows_sent（返回行数）。如果扫描 100 万行返回 10 行，必慢。
2.  **使用 EXPLAIN 分析执行计划**：
    *   对慢 SQL 执行 `EXPLAIN SELECT ...`。
    *   **重点看**：
        *   `type`：是否出现了 `ALL`（全表扫描）或 `index`（全索引扫描）？理想是 `ref` 或 `const`。
        *   `key`：实际用了哪个索引？是否为 NULL？
        *   `rows`：预估扫描了多少行？与返回行数差距是否巨大？
3.  **监控数据库状态**：
    *   在数据库服务端执行 `SHOW PROCESSLIST;`（查看当前正在执行的 SQL）。
    *   观察 `State` 列，看是否有 `Sending data`（磁盘IO慢）、`Copying to tmp table`（临时表磁盘排序）、`Waiting for table metadata lock`（表锁/DDL阻塞）等状态。
    *   通过 `SHOW GLOBAL STATUS` 对比命中率（Innodb_buffer_pool_read_requests / Innodb_buffer_pool_reads）。

---

### 第三阶段：SQL 与索引优化（治标）
聚焦于单条 SQL 的执行效率。

1.  **优化索引**：
    *   **为 WHERE 条件建索引**：哪里过滤字段多，就建联合索引（遵循最左前缀原则）。
    *   **为 ORDER BY 建索引**：避免 `filesort`（文件排序）。
    *   **覆盖索引**：`SELECT id, name FROM user` 且 `name` 有索引，让所有查询字段都在索引里，避免回表。
2.  **改写 SQL**：
    *   **避免 SELECT ***：只取需要的字段。
    *   **避免在 WHERE 子句使用函数或计算**：如 `WHERE DATE(create_time) = '2023-01-01'` 会放弃索引，应改为 `WHERE create_time >= '2023-01-01 00:00:00' AND create_time < '2023-01-02'`。
    *   **避免隐式类型转换**：`WHERE phone = 13800138000`（phone 是 varchar）会导致索引失效。
    *   **分页优化**：`LIMIT 1000000, 20` 这种深分页很慢，改用 **延迟关联**（先查主键，再 join 回原表）。
3.  **检查事务**：
    *   确认是否开启了长事务，导致 undo log 膨胀和锁等待。使用 `information_schema.innodb_trx` 查看长时间未提交的事务。

---

### 第四阶段：架构与配置优化（治本）
如果单条 SQL 已经优化到极致，但依然慢，说明是量变引发质变。

1.  **数据库配置调优（云厂商一般已优化，本地需检查）**：
    *   **innodb_buffer_pool_size**：设置为物理内存的 60%-70%。如果太小，数据频繁在磁盘和内存间换入换出，会非常慢。
    *   **max_connections**：连接数打满会导致 500 报错（连接超时）。
2.  **读写分离**：
    *   主库负责写，从库负责读。如果接口是读操作，直接把流量切到从库。
3.  **分库分表（终极方案）**：
    *   如果单表数据量超过 2000 万行，即使有索引，B+树层级变深，性能也会骤降。此时按业务维度（如user_id hash）拆分。
4.  **引入搜索引擎**：
    *   如果是模糊搜索（`LIKE '%关键词%'`）导致慢，数据库无法使用索引，应迁移到 Elasticsearch 或 ClickHouse。

---

### 第五阶段：降 500 错误的“最后一公里”
如果数据库确实优化不了，需要从代码层面兜底，避免 500 直接暴露给用户。

1.  **设置 DB 超时时间**：
    *   MySQL 驱动 `connectTimeout=5000&socketTimeout=3000`（根据业务设定），避免接口无限等待拖垮 Tomcat 线程。
2.  **熔断机制**：
    *   引入 Sentinel 或 Hystrix，当数据库异常比例超过阈值（如 50%），直接熔断，快速返回降级数据（如默认列表）而不是抛 500。
3.  **异步化**：
    *   如果接口响应慢是因为同步计算太耗时，且用户不要求强一致，改为 MQ 异步处理，接口先返回“提交成功”。

---

### 总结排查清单（建议贴墙）
遇到500且疑似DB慢，按顺序检查：

1.  **看**：慢日志里找 Top 1 SQL。
2.  **查**：`EXPLAIN` 看是否 `ALL` 扫全表。
3.  **调**：加合适的联合索引，改掉 `SELECT *`。
4.  **扩**：如果 QPS 极高，考虑 Redis 缓存或读写分离。
5.  **防**：代码里加好超时和熔断，确保 DB 挂了不会表现为 “500 服务不可用”，而是 “告警但不崩溃”。

**建议先执行：**
```sql
-- 查看当前数据库正在跑什么，是否有锁等待
SHOW FULL PROCESSLIST;
```
如果看到大量 `Waiting for table metadata lock`，先杀会话（`KILL ID;`），这往往比优化 SQL 更紧急。
